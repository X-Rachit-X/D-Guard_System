## Project Structure

The repository is organised so that one library (src/) is used by every script, the application and the tests, and every experiment is a script that reads saved predictions and writes a JSON report.

```
HealthSphere/
├── app/dguard_app.py          web application (7 views)
├── src/                       the library
│   ├── data/milk10k.py        exact loader, lesion-level split
│   ├── evidence/              opinions and Dempster-Shafer fusion
│   ├── specialists/           S4: the earlier prototype's Model A
│   ├── native/engine.py       trained network + team, one case at a time
│   ├── fusion/                Devil's Advocate, 7 fusion rules, learned gate
│   ├── calibration/           conformal sets, Learn-then-Test
│   ├── decision/              four-outcome policy, wording for patients and doctors
│   ├── agents/                quality, scribe, librarian, explainer, report, pipeline
│   ├── care/                  care workflow and SQLite store
│   ├── eval/                  metrics and image corruptions
│   ├── llm/                   optional local language model client
│   └── api.py                 REST API
├── scripts/                   experiments (one script per table)
├── notebooks/                 Kaggle training script
├── tests/                     230 automated tests
├── docs/                      documentation (14 guides)
├── paper/                     IEEE paper and figures
└── runs/                      training metrics and predictions (weights not in git)
```

The MILK10k images, the Derm7pt images, the trained weights and all generated outputs are excluded from version control: the datasets' licences do not allow redistribution, and every output can be regenerated by the scripts.

## Training the Evidential Network on Kaggle

Training needs a GPU, so it was done in a Kaggle notebook. The whole training program is a single file (notebooks/kaggle_train_dguard.py) that can be pasted into one notebook cell. It contains its own data loader, model definition, evidential loss and training loop, and writes a run folder with the best checkpoint, the training history, the configuration, test predictions and a manifest of library versions and split sizes. The manifest is checked by the local scripts: if the split reproduced locally does not have exactly the sizes recorded on Kaggle, the scripts refuse to run.

Table: Training run used in this report (seed 42).
| Item | Value |
|---|---|
| Split (train / validation / test) | 3,667 / 786 / 787 lesions |
| Best epoch | 23 of 25 |
| Best validation macro-F1 (Dempster-Shafer fusion of the heads) | 0.398 |
| Test macro-F1 locally vs on Kaggle | 0.376 vs 0.379 (a check that local inference reproduces the GPU run) |
| Library versions on Kaggle | Python 3.13, PyTorch 2.11 + CUDA 12.8 (recorded in the manifest) |

The script also supports further seeds, a dermatology foundation-model backbone, and an opt-in improved recipe (square-root class-balanced sampling, longer training), all writing to separate folders so that the main run is never overwritten. A local script (scripts/run_seeds.py) repeats the entire pipeline for any additional seed and reports the mean and standard deviation of every headline number.

## Key Implementation Details

**One code path for experiments and the application.** The fusion rules live in a single module (src/fusion/methods.py) with a common fit and fuse interface. The experiment scripts call it on hundreds of lesions at once; the application calls the same functions on one lesion. This guarantees that the system a user tries in the application is the system that was evaluated.

**Cross-fitting.** For each of the five folds, a fresh context is built from four fifths of the validation set (reliability models, track-record table, the iterative fusion's parameters), every rule is fitted, and the held-out fifth is predicted. The final models, fitted on all of validation, are saved in a single bundle with the selected rule's name, which the application loads at start-up.

**The learned gate** is a few dozen parameters per specialist, fitted with PyTorch's L-BFGS optimiser on the full batch of validation lesions in under a second. Features are standardised using statistics of the fitting set only.

**The decision policy** is a pure function of its inputs (the fused distribution, ignorance, conflict, the conformal set, the learned acquisition benefit, and the gate flags) and a versioned calibration bundle, so the same inputs always give the same decision, and every stored assessment records the policy version.

**Image checks** are written with NumPy only: the Laplacian variance as a focus measure, mean and standard deviation of the grey image, the share of saturated pixels, and the share of 8 x 8 blocks with a standard deviation below about one grey level in the central 60% of the image. Restricting the occlusion check to the centre was necessary: dermoscopic images have dark circular borders, and measuring the whole image flagged many clean dermoscopy images.

## The Web Application

The application is written in Streamlit and organised into seven views, chosen in the sidebar or opened directly with a link parameter (for example ?view=research).

![Patient view: intake, the result with its confidence tier and calibrated confidence, the "why this result" explanation, and the conversation with the doctor.](reports/screens/patient.png)

- **Patient.** Registration, opening a case, sending a photograph, dermoscopy and details (or choosing a real held-out lesion for demonstration), reading the result, answering the system's requests for more evidence (dermoscopy, details or a retake), messaging the doctor with quick questions, and deleting a case or the whole patient record.
- **Doctor.** A queue ordered by urgency; for each case, the images, the doctor-facing summary, the explanation, the specialist table and the gatekeeper showing which safety checks passed or fired, similar confirmed cases, the report, the conversation with quick replies, the timeline, and a form to confirm, override or call the patient in.
- **Compare systems.** Runs one lesion through every system (each specialist alone, every fusion rule, always-answer, the confidence threshold, the learned rejector and DERMA-GUARD) and shows the test-set comparison tables and an explanation of every evaluation metric.
- **Stress Lab.** Damages a lesion's photograph (blur, darkness, noise, JPEG compression, occlusion, removed details) and assesses the original and damaged versions side by side through the full pipeline.
- **Research.** Every experimental result with confidence intervals, including the external tests and the re-evaluation of the earlier prototype.
- **Architecture.** The pipeline diagram and a table mapping each component to its source file.
- **System.** Platform statistics, the audit log and a reset of the demonstration database.

## Testing

The project has 230 automated tests that run in about ten seconds without any dataset or trained weights, using small synthetic inputs. They check mathematical properties (for example, that belief and ignorance always sum to one and that a vacuous opinion leaves Dempster's rule unchanged), statistical guarantees on synthetic data (conformal coverage, the Learn-then-Test bound), decision logic (every gate, every outcome, cost asymmetry), the care workflow (routing, queue order, follow-ups, change alerts, deletion), and the agents (quality checks, red flags with negation, the explanation verifier). The full pipeline was additionally checked end to end: the application's seven views were rendered headless with Streamlit's testing framework without errors, and the "ask for details, then reassess" flow was run through the real care service.
